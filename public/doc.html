Proxy Server Log Tool — TypeScript Code Documentation

A local TypeScript + Node.js reverse proxy that intercepts every HTTP and SOAP call between a front-end and its backend APIs, captures full request/response headers and bodies to date-partitioned disk folders, streams them live to an integrated inspection dashboard (Monaco editors), and lets you replay any captured request with custom overrides.

TypeScript 5.9 Node.js + Express 4 http-proxy 1.18 Date Partitioned: YYYY-MM-DD Vector SVGs Main proxy :4000 Redirect proxies :4001+

01 Bird's-Eye View

The problem it solves

When developing a web front-end against multiple backend microservices (REST or SOAP), you constantly need to answer: what exactly was sent, what came back, how long did it take? This tool sits on localhost:4000. You point your Vite dev-server proxy (or browser) at it; it forwards traffic to the right backend while keeping a permanent, browsable record of every exchange in date-partitioned folders.

One process, several faces

A single Express server written in TypeScript exposes multiple surfaces on the same port:

1. Reverse Proxy (default)

Every unmatched path falls through to proxyEngine.proxyMiddleware, which picks an app + backend by path prefix and relays the call (server.ts:51).

2. Admin REST API

/dashboard-api/* manages applications, storage paths, dates, logs, export, replay, redirect proxies and a Server-Sent-Events stream (src/routes/api.ts).

3. Static Dashboard SPA

/dashboard serves public/index.html; assets under /dashboard-static/*; docs at /doc.

4. Redirect Proxy Servers

Each configured external forwarding target gets its own dedicated proxy server on an auto-assigned port (:4001+) (src/services/redirectProxyManager.ts).

Key capabilities

  • TypeScript Strict Safety: every service, route, and entity is strictly typed with shared interfaces in src/types/index.ts.
  • Date-Partitioned Storage: captures are organized in logs/YYYY-MM-DD/ and headers/YYYY-MM-DD/, loading only the latest day on boot for fast startup (src/services/logManager.ts).
  • Period & Date Selector: top navbar allows switching between captured days seamlessly without restarting the server.
  • Prefix-based routing: each configured backend declares a pathPrefix; the longest matching prefix wins (src/services/proxyEngine.ts).
  • Live feed: new captures are pushed instantly to open dashboards via SSE — including captures from redirect proxies.
  • Inspect: Monaco editor panes auto-detect JSON/XML and pretty-print; cookie headers get special treatment.
  • Replay: re-fire any captured call with edited URL/method/headers/body (src/services/replayService.ts).
  • Export: save a request/response pair straight into the user's Downloads folder.
  • Archive: move captured logs for an application into an archives/ directory organized by app name, preserving them without deletion (src/services/logManager.ts).
  • Redirect proxies: apps can declare external API forwarding rules (e.g. payment gateway) that run on dedicated ports, still fully captured and streamed.
  • Configurable storage: where config/, logs/, headers/ and archives/ live can be changed via env vars, settings.json or the dashboard.
  • Loading indicators: a global shimmer bar, section-level blur overlays, button spinners and error toasts give visual feedback for every dashboard operation (public/js/app.js).
  • Vector SVGs: all UI icons use scalable inline vector SVGs inheriting currentColor for dark & light modes.
Mental model: think "Charles Proxy / Fiddler, but self-hosted in TypeScript & Node.js, configured by a JSON file, with a web UI instead of a desktop app."

05 Proxied Request Lifecycle (end to end)

  1. A client hits any path on port 4000. Express middleware chain runs: CORS → compression → admin API → static → dashboard/doc → root redirect; everything else reaches proxyMiddleware (server.ts).
  2. The middleware captures the raw request body with memory safety protection (src/utils/payload.ts), stashing req._proxyRawBodyStr and req._proxyRawBuffer (src/services/proxyEngine.ts).
  3. It resolves the effective path, optionally stripping an explicit /proxy/:appId prefix, then retrieves active apps from in-memory configuration cache (src/services/configManager.ts).
  4. Target selection cascade:
    • a) explicit app id from route param, x-proxy-app-id/x-app-id header or _appId query;
    • b) global scan of every active backend across all active apps, matched by longest pathPrefix first; backends with no prefix act as catch-alls. Redirections are excluded here — they have their own ports;
    • c) fallback: match app whose frontEndUrl appears in Referer/Origin, use its first backend;
    • d) still nothing → 404 listing the configured prefixes.
  5. Request is stamped with correlation state: _proxyRequestId (UUID), _proxyStartTime, _proxyApp, _proxyBackendService, _proxyTargetUrl.
  6. The buffered body is wrapped in a PassThrough stream (it was already consumed) and handed to proxy.web(req, res, { target, buffer }).
  7. Upstream responds. Because selfHandleResponse: true, the proxyRes handler collects chunks, computes duration, and calls logManager.saveLogEntry which writes the four files in the day's date folder YYYY-MM-DD.
  8. A compact summary is broadcast to every SSE subscriber.
  9. Status code plus upstream headers are copied to the client — except content-length / transfer-encoding — and the buffered body is flushed with res.end(buffer).
  10. The dashboard's EventSource receives the summary, filters by the currently selected app, and prepends it to the list. Clicking a row fetches /dashboard-api/logs/:id?date=YYYY-MM-DD and renders bodies into the Monaco panes.
  11. If upstream is unreachable, the error handler records a FAILED capture with status 502 and answers the client with a JSON error.

Redirect proxy lifecycle

A request to a redirect port (http://localhost:4001, etc.) never touches proxyMiddleware. The subscriber app is resolved from the x-proxy-app-id/x-app-id header, the Referer/Origin, or the first subscriber of that shared port (src/services/redirectProxyManager.ts), then the request flows through the same buffer → log → broadcast → forward pipeline of that port's own http-proxy instance.

06 Practical Integration Guides & Examples

Here are real-world recipes showing how to connect your front-end apps, route microservices, handle external payment/OAuth redirects, and test with cURL.

6.1 Single-Page App (SPA) Integration — Vite, React, Vue, Angular

When developing a front-end SPA, configure your dev server proxy to forward all API calls through ProxyServerApp (http://localhost:4000).

vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    port: 3000,
    proxy: {
      // Forward all /posts and /api calls to ProxyServerApp
      '/posts': {
        target: 'http://localhost:4000',
        changeOrigin: true
      },
      '/api': {
        target: 'http://localhost:4000',
        changeOrigin: true
      }
    }
  }
});

In your React/Vue components, simply make standard API calls:

src/services/api.ts (Frontend)
// Browser sends GET http://localhost:3000/posts/1
// -> Vite dev server proxies to http://localhost:4000/posts/1
// -> ProxyServerApp matches prefix '/posts' -> https://jsonplaceholder.typicode.com/posts/1
// -> Proxy logs headers, status, duration, and body -> streams to Monaco Dashboard -> responds to browser
const response = await fetch('/posts/1');
const post = await response.json();
console.log('Fetched Post:', post);

6.2 Multi-Backend Microservices with Path Prefixes

An application can define multiple backend targets with different path prefixes. ProxyServerApp routes requests using a longest matching prefix algorithm.

Application Config with Multiple Backends
{
  "id": "app-ecommerce",
  "name": "E-Commerce App",
  "frontEndUrl": "http://localhost:3000",
  "backendUrls": [
    {
      "id": "be-auth",
      "name": "Auth Service",
      "url": "http://localhost:5001",
      "pathPrefix": "/api/v1/auth"
    },
    {
      "id": "be-catalog",
      "name": "Product Catalog Service",
      "url": "http://localhost:5002",
      "pathPrefix": "/api/v1/products"
    },
    {
      "id": "be-orders",
      "name": "Order Management Service",
      "url": "http://localhost:5003",
      "pathPrefix": "/api/v1/orders"
    }
  ],
  "isActive": true
}

How the proxy routes incoming requests:

  • GET /api/v1/auth/login → routed to http://localhost:5001/api/v1/auth/login
  • GET /api/v1/products/42 → routed to http://localhost:5002/api/v1/products/42
  • POST /api/v1/orders → routed to http://localhost:5003/api/v1/orders

6.3 External 3rd-Party APIs (Dedicated Redirect Proxy Ports)

For external SaaS APIs (such as Stripe, PayPal, SendGrid, or AWS S3), ProxyServerApp starts a dedicated proxy on an assigned port (e.g. 4001).

Redirect Rule Configuration
{
  "id": "redir-stripe",
  "name": "Stripe Payments API",
  "targetUrl": "https://api.stripe.com",
  "port": 4001
}

In your backend or frontend test code, point the SDK host to localhost:4001:

Testing External API Calls (cURL or SDK)
# Make a call to Stripe through the dedicated redirect proxy port
curl -X POST http://localhost:4001/v1/charges \
  -H "Authorization: Bearer sk_test_12345" \
  -d "amount=2000" \
  -d "currency=usd"

# Result: Request is forwarded securely to https://api.stripe.com/v1/charges.
# Full request body, headers, and Stripe's JSON response are intercepted, saved to disk,
# and rendered live on http://localhost:4000/dashboard with a yellow [Redirect] badge.

6.5 Replaying & Modifying Captured Calls

You can replay any past transaction directly from the UI or via the Replay API (POST /dashboard-api/logs/:id/replay). This lets you test backend error handling, override auth tokens, or tweak payload bodies without reloading your browser application.

Replay with Custom Overrides via API
curl -X POST http://localhost:4000/dashboard-api/logs/a1b2c3d4-e5f6-7890-abcd-ef1234567890/replay \
  -H "Content-Type: application/json" \
  -d '{
    "customMethod": "POST",
    "customHeaders": {
      "authorization": "Bearer updated-debug-token",
      "x-custom-test": "true"
    },
    "customBody": "{\"testOverride\": true}"
  }'

07 Admin API & SSE Feed

Design notes

  • router.use(express.json()) parses bodies only for these administrative endpoints (src/routes/api.ts:19) — proxied traffic never goes through here because the proxy middleware consumes it first.
  • All CRUD delegates to src/services/configManager.ts / src/services/settingsManager.ts; validation errors surface as HTTP 400, missing resources as 404.
  • Every application create/update/delete re-runs src/services/redirectProxyManager.ts so redirect servers mirror the stored config immediately.
  • The trailing catch-all inside the router calls next(): unknown paths such as /api/users intentionally fall out of /dashboard-api and continue toward the proxy.

Settings API

  • GET /dashboard-api/settings returns the effective paths plus flags (isDefaultConfig, isDefaultLogs) and the defaults.
  • PUT /dashboard-api/settings accepts configDir, logsDir and migrateExistingConfig; it persists to settings.json, optionally copies applications.json, and re-syncs redirect proxies.

Date & Logs API

  • GET /dashboard-api/logs/dates returns an array of all available YYYY-MM-DD subfolder names sorted descending.
  • GET /dashboard-api/logs?appId=&date=&q= lists captured log entries. By default, it automatically selects the newest available date folder for fast initial rendering.
  • GET /dashboard-api/logs/:id?date= fetches full detail for a log in that specific date folder.

SSE channel mechanics

  • GET /dashboard-api/events sets the three canonical SSE headers and registers the res object in sseClients[] (src/routes/api.ts:220, src/services/proxyEngine.ts).
  • On socket close the client is removed, preventing memory leaks.
  • broadcastLogEvent writes data: {JSON}\n\n to each subscriber, swallowing per-client write errors.
  • server.ts:82 hands the same sseClients array to redirectProxyManager, so redirect-port captures appear in the same unified live feed.

Replay semantics

The endpoint accepts optional overrides (customUrl/customMethod/customHeaders/customBody); anything omitted is taken from the stored capture. System headers that break outbound fetches (host, content-length, connection, accept-encoding) are stripped before sending (src/services/replayService.ts).

09 Data Model & Date-Partitioned Storage

config/applications.json

Written by configManager.saveApplications with 2-space indentation. Shape:

application entry
{
  "id": "app-default-1",                       // stable id (uuidv4 unless provided)
  "name": "Sample JSON Store API",
  "frontEndUrl": "http://localhost:3000",      // used by the Referer fallback matcher

    { "id": "be-1", "name": "JSON Placeholder API",

settings.json (optional)

src/services/logManager.ts:28-45

Date partitioning helper

export function getDateFolder(dateInput?: string | Date): string {
  if (typeof dateInput === 'string' && /^\d{4}-\d{2}-\d{2}/.test(dateInput)) {
    return dateInput.slice(0, 10);
  }
  const d = dateInput ? new Date(dateInput) : new Date();
  const year = d.getFullYear();
  const month = String(d.getMonth() + 1).padStart(2, '0');
  const day = String(d.getDate()).padStart(2, '0');
  return `${year}-${month}-${day}`;
}

Guarantees uniform YYYY-MM-DD subfolder names across both logs and headers directories.
